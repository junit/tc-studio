# PDF 报告生成故障与修复

> 本文记录第一轮故障。随后会话 114 / 116 又出现字体与可读性问题，已确认是实际服务解释器缺少 ReportLab、
> 手工 PDF 字体结构错误，以及发布校验覆盖不足。当前修复、真实文件证据和 410 项回归结果见
> [PDF 运行环境与 BOT 状态复查](PDF_RUNTIME_AND_BOT_STATUS_FOLLOWUP.md)。下文的 349 项是第一轮历史结果。

## 已确认的现象

2026-11-12，内建助手 `default_assistant` 的同一会话两次收到“生成 PDF 报告”。
证据来自 SQLite 中序列 107–112 的会话消息、代码执行记录、附件元数据，以及保留在上传目录的原始产物。
原 12B 文件已经被第二轮的同名文件覆盖，不能再把当前文件的大小当作第一轮文件的大小。

| 项目 | 实证 | 结论 |
|---|---|---|
| 第一轮 12B 附件 | 序列 108 的附件元数据为 12B。真实 spawn/RPC 回归在修复前收到 `<bytes:49>`，而非传入的 49 个字节；6340 字节会被编码为 12 字符的 `<bytes:6340>` | 二进制被有损摘要替换，平台把摘要文字保存成 PDF，确凿证实 |
| 第一轮英文补救文件 | 现存文件 6340B，严格解析得到 2 页，Poppler 渲染成功 | 并非该轮所有链接都损坏；自动追加的 12B 中文附件是无效产物 |
| 第二轮中文文件 | 现存 10979B、2 页，严格解析及文本提取成功；实际渲染出现重叠和裁切。pdfplumber 检测到第 1 页 320、第 2 页 119 个字符越界 | 能读出文字不代表页面可读，确凿证实 |
| 字号异常 | 回放当时的全局 `size=22` 与 `PDFBuilder2` 代码，默认正文被写成 22pt，行距仍为 16pt；未按行宽换行 | AST 执行器在该场景下受全局同名变量影响，且临时排版算法缺少宽度布局；两者一起放大了问题 |
| 附件状态陈旧 | 第二轮正式文件元数据仍为初次写入时的 13B；`_test_pdf.pdf` 元数据为 10989B，但被后续代码清空，现存文件为 0B | 产物列表只追加、不刷新，确凿证实 |
| 执行日志错误 | 会话中带 `print` 的步骤被展示为“无标准输出”。最小事件回放证明：`ActionOutput.output=None` 提前占用步骤日志，后续 `ActionStep.observations` 被跳过 | 展示与持久化日志不完整，确凿证实 |

这是文件生成、沙箱传输和产物归集链路的问题；现有证据没有指向 SQLite 数据损坏。

## 修复后的调用方式

普通会话和协同子任务都提供以下能力：

```python
result = create_pdf_report(
    "直播诊断报告.pdf",
    "直播诊断报告",
    "## 结论\n已有诊断结论。\n\n| 检查项 | 结果 |\n|---|---|\n| 推流状态 | 待核验 |",
)
print(result["size"])
final_answer(f"报告已生成：[下载]({result['download_url']})")
```

`filename` 必须以 `.pdf` 结尾；标题最多 200 字符，正文最多 200000 字符。
支持中文/英文标题、段落、引用、列表和管道表格。简单 `echarts` 的 `labels/data`
转为静态数据表，便于 PDF 阅读；不执行 JavaScript。原生复杂 ECharts 配置不会成为交互式图表。
中文字体随代码分发并嵌入使用字形的子集，不依赖宿主系统字体或运行时下载。
字体来源、固定提交、SHA-256 与 OFL 许可见 `core/agent/assets/fonts/`。
装饰性 emoji 会省略，常用对勾、叉、警告和星级转换为字体可显示的等价字符；
正文出现其他缺失字形时明确报错，避免静默输出方框。

模型只负责报告文字。字体路径、HTML、图片、CSS、远程资源与 PDF 对象结构不作为模型可配置项。
库通过服务端能力调用，未加入沙箱导入白名单，也没有向沙箱暴露客户端、系统字体目录或凭据。

## 数据传输和文件发布

- 工具参数使用独立的有界 JSON 编解码器。`bytes/bytearray` 通过带类型的 base64 信封传输；
  普通字典若与协议标记同名会被转义，不能误解码。超过大小或深度上限直接失败，不截断数据后宣称成功。
- spawn、父进程 nsjail 通道和 nsjail worker 共用相同的编解码规则，保持 JSON 边界，不使用 pickle。
  现有 IPC 帧上限仍为 8 MiB，二进制的 base64 开销也计算在内；这不代表单次 RPC 可以上传 100 MiB。
  `create_pdf_report` 在服务端生成文件，只需要传输正文和小型结果元数据。
- 状态快照仍使用有界摘要；它用于观察与会话缓存，不再充当工具参数编码器。
  任意 Python 对象和大二进制变量的跨轮完整持久化不在本次修复范围内。
- PDF 保存先写临时文件，检查文件头、EOF、严格结构解析、页数和加密状态，再原子发布到独立版本名。
  页数上限 500、PDF 文件上限 64 MiB。校验失败删除临时文件并保留先前有效产物。
- 会话最终附件只包含明确发布的文件；普通 `save_file` 和 `open` 写入临时工作区，
  不扫描整个目录自动追加探测文件。`create_pdf_report` 自带正式发布和 SQLite 文件登记。
  同名文件产生独立版本和稳定下载地址，保留配额及目录约束。
- `ActionOutput` 没有表达式结果时等待 `ActionStep` 的真实 observations，避免空日志遮蔽标准输出。

`save_file` 对任意 PDF 做的是结构校验，无法单凭结构证明任意第三方 PDF 的视觉质量。
报告排版应使用 `create_pdf_report`；仍需针对最终文件做渲染检查，不能用文本提取成功替代。
此次没有全局修改第三方 AST 执行器的默认参数语义；报告工具在服务端执行，避开了该问题。

## 验证方法

```bash
rtk proxy uv sync --locked
rtk proxy env PYTHONPATH=. .venv/bin/python -m pytest -q tests/test_pdf_generation.py
rtk proxy uv lock --check
rtk proxy uv pip check --python .venv/bin/python
```

全量测试应在独立代码副本运行，避免触碰正在使用的配置、会话与上传文件。
旧兼容性测试会主动设置 `APP_ENV`、`AUTH_ENABLED`、`TIM_CONFIG_PATH` 等变量；
若运行器额外固定对应的 `TC_STUDIO_*` 变量，会按命名空间优先级覆盖测试设定并制造失败。

最终报告额外使用 Poppler 渲染全部页面，再逐页检查；使用 pdfplumber 检查字符是否越过纸张边界。
Poppler/pdfplumber 是本地验收工具，生产 PDF 生成无需安装它们。

## 回归矩阵

| 用例 | 必须满足的断言 |
|---|---|
| 二进制 spawn/RPC | 包含 NUL、0xff 的原始字节完整到达 `save_file`，不变成 `<bytes:n>` |
| nsjail 双向编解码 | 同样的字节与包含协议标记的普通字典往返不变 |
| 大小与条目边界 | 超限明确报错；1200 项列表完整传输，不在 1000 项处静默裁切 |
| 同名版本与临时文件 | 同名正式文件分别保留；探测文件不出现在最终回复和持久化附件中 |
| 无效 PDF 发布 | 摘要文字、截断 PDF 不进入正式产物；覆盖失败保留有效旧文件；无临时文件遗留 |
| 中文、英文与长表格 | 字体实际嵌入；长行换行、表格跨页；最终 PDF 坐标与行距无越界或重叠 |
| 不可信标记 | `<img>`、`<font>` 等按文字显示，不访问远程资源，不允许改变字号或布局 |
| 图表静态化 | 简单 ECharts 的标题、时间与数值完整保留，正文不泄露 JSON 配置代码 |
| 空内容与输入上限 | 空标题、空正文、201 字符标题、200001 字符正文直接拒绝 |
| 真实执行器报告调用 | 即使模型会话全局已有 `size=22`，服务端正文布局仍保持正常 |
| 下载一致性 | HTTP 返回的 MIME、attachment 响应头和文件字节与最终发布内容一致 |
| 显式发布 | 直接写入的无效 PDF、原子临时文件不被当作正式成果 |
| 执行证据 | 真实打印的文件大小出现在持久化执行日志，而非“无标准输出” |

## 修复副本与边界

修复副本写在本地 `output/pdf/`，以最近一次已保存的诊断正文重新排版。
原上传 PDF 与原始会话保持为故障证据；修复副本不会替换历史附件。
此次只验证 PDF 生成、布局、传输和下载，不重新调用腾讯云接口，也不替原业务归因做新的事实背书。
依赖及字体随后端更新一起发布；不支持自动重载的部署需要重启后端以加载新能力。
Linux/nsjail 主机级隔离及线上模型端到端重跑不由本地解析与渲染测试替代。
